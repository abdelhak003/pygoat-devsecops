# PyGoat DevSecOps — End-to-End Security Pipeline

University DevSecOps project: a traditional CI/CD pipeline turned into an **end-to-end, policy-driven
security workflow** around [PyGoat](https://github.com/adeyosemanputra/pygoat), an *intentionally
vulnerable* Django application.

> **Scope, stated honestly.** This is a university / portfolio implementation (final-year cybersecurity
> engineering project), built and run on GitLab CI/CD. It is not enterprise production experience.
> PyGoat is a deliberately vulnerable training application: some vulnerable lab pages remain **on
> purpose** as teaching material, and they are reported as non-blocking warnings.

---

## 1. Objective

Take an application with a large number of real security findings and build a pipeline that:

- **detects** issues as early as possible (developer workstation → CI);
- **decides automatically**, through a versioned security policy, whether a release may proceed;
- **blocks** anything above the policy thresholds before production;
- **makes every decision visible and auditable** (reports, dashboard, notifications, exception register);
- then **remediates** the findings until the security gate passes.

## 2. Architecture

```
 Developer
    │  git commit
    ▼
 Pre-commit hooks (shift-left)          Gitleaks · Bandit · Semgrep · private-key detection
    │  git push
    ▼
 GitLab CI/CD ─────────────────────────────────────────────────────────────────────────────
    │  secrets_scan → sast → scan_dependencies → iac_scan → build → test → package
    │  → docker_scan → sbom → dast
    ▼
 Security scanners  ──►  full JSON reports (every severity, kept as artifacts)
    ▼
 Security Gate  (ci/security_gate.py + ci/security-policy.toml + ci/exemptions.toml)
    │        PASS / BLOCKED
    ├──────────────►  Grafana Cloud dashboard (OTLP metrics)      — visualises
    ├──────────────►  Slack alerts                                — notifies
    ▼
 Manual production promotion (deploy:production, human approval, only if the gate passed)
```

**Scanners detect → Security Gate decides → Grafana visualises → Slack notifies.**
Neither Grafana nor Slack can influence a release: `deploy:production` depends only on the
`security_gate` job.

## 3. Security controls

| Area | Tool | What it checks | Blocking rule (policy) |
|---|---|---|---|
| Secrets | **Gitleaks** 8.30 (+ custom rules) | keys, tokens, passwords in code | zero tolerance |
| SAST | **Semgrep** (p/python, p/django, p/secrets) | injection, RCE, insecure patterns | severity `ERROR` |
| SAST | **Bandit** | Python-specific risks (eval, pickle, shell=True…) | `HIGH` with confidence ≥ `MEDIUM` |
| SCA | **Trivy fs** | vulnerable Python dependencies | CVSS ≥ 7.0 **and** a fix exists |
| IaC | **Trivy config** + **Checkov** | Dockerfile misconfigurations (root user…) | HIGH/CRITICAL; CIS Docker 4.1 checks |
| Container | **Trivy image** | OS and library CVEs in the built image | CVSS ≥ 7.0 **and** a fix exists |
| SBOM | **CycloneDX** (generated by Trivy) | inventory of image components | informational artifact |
| DAST | **OWASP ZAP** baseline | the running application | ZAP risk `High` |

Same controls on the developer workstation through `.pre-commit-config.yaml` (Gitleaks, Bandit,
Semgrep, private-key detection). `git commit --no-verify` can bypass local hooks, which is exactly why
the same checks run again in CI, where they cannot be skipped.

## 4. Security decision: policy as code

- **`ci/security-policy.toml`** — the single source of the blocking thresholds for every tool
  (blocking / warning / info). Changing a threshold is a reviewed code change.
- **`ci/security_gate.py`** — Python standard library only. Parses every scanner report, normalises
  findings, applies the policy and the exception register, and produces:
  - the decision (`exit 1` = BLOCKED);
  - `reports/security-summary.json` (machine-readable, consumed by Grafana and Slack);
  - `reports/security-summary.md` and a **JUnit** report (each blocking finding appears in GitLab's
    *Tests* tab).
- **Fail-secure:** a missing scanner report counts as a blocking finding (`MISSING`), and a malformed
  exception register blocks the gate. Absence of evidence is never treated as absence of risk.
- Each scan job also evaluates its own control, so developers get fast, per-tool feedback.

## 5. Results

| Snapshot | Blocking findings | Gate |
|---|---|---|
| Initial baseline | **1104** | BLOCKED |
| Base image, non-root container, dependencies | 29 | BLOCKED |
| Runtime packaging tools removed from the image | 25 | BLOCKED |
| Hard-coded secrets removed | 12 | BLOCKED |
| Application findings remediated | **0** | **PASS** |

**1104 → 29 → 25 → 12 → 0: a 100 % reduction in the blocker count under the defined security policy.**
This measures policy violations removed; it is **not** a claim that the application is "100 % secure".
Non-blocking warnings remain visible and are tracked; several are intentional training labs.

Initial blockers by control: Trivy image 994 · Trivy fs 83 · Gitleaks 13 · Semgrep 8 · Bandit 4 ·
Trivy config 1 · Checkov 1 · ZAP 0. The validated snapshots and their provenance are versioned in
`monitoring/history/security-history.json`.

## 6. Remediation examples

**Container and supply chain**
- Multi-stage image on `python:3.11-slim-bookworm`; build tools kept out of the runtime stage.
- `pip`, `setuptools` and `wheel` removed from the runtime image.
- Dedicated **non-root** user (uid 10001); application code not writable by that user; `HEALTHCHECK`.
- Vulnerable dependencies upgraded (e.g. Django 5.2 LTS and related packages).

**Secrets**
- The hard-coded Django `SECRET_KEY` removed: the key comes from the environment (masked GitLab CI/CD
  variable); the application refuses to start without it (no silent fallback).
- Lab signing keys derived from the secret key (`salted_hmac`) instead of hard-coded strings.

**Application code** (secure redesigns that keep the labs educational)
- **Command injection:** lab commands are simulated or run without a shell; inputs validated.
- **Unsafe deserialization:** `pickle.loads()` on a cookie replaced by server-signed JSON tokens
  (`django.core.signing`); no Python object is ever built from user input.
- **Unsafe YAML:** `yaml.load` with the full loader replaced by `yaml.safe_load`.
- **`eval()` removed:** an AST allowlist for the calculator lab; expressions explained, not executed.
- **Learner code treated as data:** parsed with `ast` and reviewed, never written to disk or executed.
- **SSRF:** outbound requests restricted to HTTPS public destinations, with DNS resolution checks and IP
  pinning.
- **JWT handling:** signing key derived from the secret key; explicit algorithm on decode.
- **Password hashing:** lab passwords stored with Django hashers and verified with `check_password()`.
- **SSTI:** blog posts stored as data and rendered with Django auto-escaping, never compiled as templates.
- **XSS hardening:** simulated command output that pages insert with `innerHTML` is HTML-escaped; CSRF
  tokens added to the lab API calls. (PyGoat's intentional XSS lab pages remain as training material.)

## 7. Governance: controlled false-positive exceptions

Disabling a scanner or lowering a threshold hides future issues too. Instead, `ci/exemptions.toml`
records **temporary, traceable acceptances of one specific finding**:

- **exact matching** on the control **and** a stable fingerprint `<rule>|<location>` (no wildcards);
- mandatory **owner**, a **different approver** (four-eyes principle), **ticket** reference and
  **justification**;
- **expiration ≤ 90 days**; an expired exception simply stops applying (the finding blocks again);
- exempted findings stay **visible** (summary, Markdown, JUnit "skipped" with the exception ID);
- malformed register → gate **BLOCKED** (fail-secure).

**The final baseline has no active exception:** every blocker was fixed, not suppressed.
The mechanism is demonstrated with synthetic data only:

```bash
python -m ci.tests.demo_exemption_workflow    # BLOCKED → EXEMPTED/PASS → expired → BLOCKED
```

Details: `docs/devsecops/06-exemptions.md`.

## 8. Observability and notifications

**Grafana Cloud** — `ci/security_telemetry.py` sends low-cardinality OTLP metrics after every gate run;
the dashboard `monitoring/grafana/pygoat-sentinel-dashboard.json` shows:
gate status (PASS / BLOCKED), release status, blockers and warnings per control, gate history,
control status matrix (including missing evidence), the remediation trend 1104 → 0 and a
before/after comparison.

**Slack** — `ci/slack_notify.py` (Incoming Webhook, secret kept in a masked CI variable, never printed):
- 🟢 **RELEASE AUTHORIZED** — gate PASS; promotion still requires manual approval;
- 🔴 **RELEASE BLOCKED** — gate BLOCKED with the number of blocking findings;
- 🚀 **PRODUCTION PROMOTED** — after a successful manual promotion.

Both integrations only *read* the gate's result. If Grafana or Slack is unavailable, the job is marked
as a tolerated failure and the release decision is unchanged.

Details: `docs/devsecops/07-observability.md`, `docs/devsecops/08-notifications.md`.

## 9. Production

In this project, **production means the manual promotion of the validated Docker image**: the
`deploy:production` job (default branch, manual approval, only after the security gate passes) tags the
image that was scanned and tested as `:production` in the GitLab Container Registry. **No public
production server is deployed.**

## 10. Live demo scenario

1. Introduce a vulnerable `subprocess.run(user_input, shell=True)` in a demo module.
2. `git commit` → **pre-commit blocks** it (Bandit + Semgrep).
3. Deliberately bypass the hooks with `git commit --no-verify` and push.
4. **GitLab CI detects it again** → the Security Gate is **BLOCKED** → Slack 🔴 RELEASE BLOCKED;
   `deploy:production` is not available.
5. Fix the code (no shell; input handled as data) → push → rescan → **PASS** → Slack 🟢.

The demo module in this snapshot (`demo/demo_command_injection.py`) is the **fixed** version.


Run the tests locally:

```bash
pip install -r requirements.txt
export DJANGO_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(50))')"
python manage.py test               # application + pipeline tooling tests
```
